## 1. Coarse first pass (authors' account; artifacts not retained)

According to the authors (rebuttal notes, 2026-09-26), four annotators (all co-authors; three CS undergraduates) each read a **different** set of 200 trajectories (800 in total) and, from that reading, agreed on three broad root-cause groups and an initial codebook consensus. **Not retained:** the per-annotator 200-trajectory assignments, the notes or codes produced in this pass, and the wording of the three groups. No file in the repository is dated to or labelled as this pass, so no count of codes from it is reported here.

What the retained files do show is the *result* of that consensus, i.e. the v1 scheme (next section). Its top-level `primary_failure_layer` field has three dominant values (`model` 973, `agent` 114, `environment` 59; `task` 3) over the 1149 retained v1 objects. This is consistent with a three-group origin but is not by itself proof that these were the three groups of the coarse pass.

## 2. v1 applied to the full corpus, and the problems it exposed

### 2.1 What v1 was

v1 is a **single-marker, FAIL-only** scheme: one root-cause triple (`primary_failure_layer` / `primary_failure_category` / `primary_failure_subtype`), an optional contributing triple, a free-text `root_cause_label`, a reasoning paragraph, and exactly one step index `n` (stored as `command_index_ratio.n`, with `m` = length). Only `layer` (4 values) and `category` (11 values) were vocabulary-controlled; `subtype` was free text and realised 783 distinct strings over 1149 records. Full field list and frequencies: `v1_schema.md`.

The authors list four problem types: multiple errors, recovered errors, category boundaries, and insufficient coverage. The retained v1/v2 pairs let us show each one on real cases (v1 `n` vs v2 `t_err`/`t_commit`; 1052 FAIL pairs with identical step count `m` in both rounds are used for step comparisons).

The boundary problem persisted into the retained v1 taxonomy fields of v2: because the v2 prompt typed `primary_failure_layer/category` as free strings, the v2 annotator coined values outside the 11-value v1 vocabulary in 38/1148 pairs (57 distinct categories overall). Two examples:

#### (d) Insufficient coverage

- **PASS trajectories**: v1 annotated FAIL only (all 1149 retained v1 objects have `outcome = fail`); the 610 PASS trajectories had no annotation at all before v2.
- **FAIL trajectories without a v1 object**: 36 of the 1184 final FAIL trajectories carry no `v1_annotation` (by scaffold/model: miniswe/deepseek-v3.2 17, miniswe/gpt5 13, terminus2/gpt5 2, terminus2/kimi 1, terminus2/qwen 1, terminus2/deepseek-v3.2 1, miniswe/claude 1). Why they were missed in v1 is **not retained**. Examples: `add-benchmark-lm-eval-harness__miniswe__gpt5`, `add-benchmark-lm-eval-harness__terminus2__gpt5`.
- **Silent failures**: v1 had no field for whether a failure signal ever surfaced. In v2, `t_surface` is null in 332/1184 FAIL records. Two long silent cases that v1 could only summarise in prose: `extract-moves-from-video__terminus2__devstral` (m=575, v1 n=6, v2 t_err=8, t_commit=8); `add-benchmark-lm-eval-harness__openhands__gemini` (m=294, v1 n=43, v2 t_err=43, t_commit=48).
- **Fabrication**: not a v1 field. A separate audit pre-flagged 264 cases (`fabrication_info` in the index; 264 of them have a v1 object); v2 made `fabrication_present/type/onset_step/evidence` part of the schema.
- **Invalid marker values**: 2 v1 objects have n = 0 (outside the 1-indexed range): `build-cython-ext__miniswe__qwen` (v2 t_commit=16), `neuron-to-jaxley-conversion__openhands__deepseek-v3.2` (v2 t_commit=25).
- **Outcome inconsistency**: 1 case(s) are `fail` in v1 but PASS in the final index/v2: `modernize-fortran-build__terminus2__deepseek-v3.2`. The reason (re-run or re-scored outcome) is **not retained**.
- **Step count drift**: v1 `m` differs from v2 `m` in 96 pairs (v1 shorter in 83), concentrated in `build-cython-ext` 8, `chess-best-move` 8, `play-zork-easy` 8, `count-dataset-tokens` 7, `neuron-to-jaxley-conversion` 7, `parallelize-graph` 7. The transcripts used in v1 for these cases are **not retained**, so their markers are not step-comparable.

## 3. Revision (what changed in the codebook)

The revision is documented by the v2 prompt frozen in `CODEBOOK.md` section 6 and by the field diff in `v1_schema.md` section 4. Discussion minutes and intermediate drafts of the codebook are **not retained**. The changes that the files prove:

1. **Time definition split in three.** The single `n` became `t_err` (decisive mistake), `t_commit` (lock-in; the prompt states 'Same as v1 field n'), and `t_surface` (first observable signal; null = silent), each with a verbatim evidence quote and a `timepoint_confidence`. Invariant `1 <= t_err <= t_commit <= m` enforced (`validate_v2.py`, C1-C4).
2. **Controlled mechanism vocabulary (8+1).** `trigger_mechanism` with eight defined values plus `other` (requires `trigger_mechanism_other`), replacing the free-text subtype as the analysable root-cause field.
3. **Process fields.** Forewarning (types + first step strictly before t_commit), awareness after t_commit, tail behaviour, fabrication, verification, and `action_segments` covering every step.
4. **PASS schema.** A separate success-characterisation schema (error events, recoveries, detours, near-miss, suspicious pass, directness) so that recovered errors in successful runs are recorded.
5. **Bookkeeping.** `schema_version`, `long_traj` (sampling rule for m > 120), `uncertain_fields`. Task-level metadata (`task_category/difficulty/type`) and `reasoning_en` dropped from the annotation object.

Not changed: the v1 taxonomy triple and `root_cause_label` were kept in the FAIL schema as free strings (see 2.3(c) for the consequence).

## 4. v2 re-annotation of the whole corpus

- All 1794 trajectories in `traj_data_v2_all89tasks.json` carry `schema_version = v2`: 1184 FAIL, 610 PASS. The v1 object, where it existed (1149 cases), was supplied as context; the annotator re-judged independently (`CODEBOOK.md` section 1).
- Realised vocabularies and the 16 invariants (0 violations) are in `CODEBOOK.md`; `uncertain_fields` was used on 1052 field-flags across FAIL records (top: `t_err` 295, `t_commit` 183, `t_surface` 180, `forewarning_first_step` 131).
- **Agreement of the kept marker with v1.** On the 1148 FAIL pairs, t_commit = n exactly in 45.8%, within +/-1 in 55.2%, within +/-3 in 64.5%; |d| > 5 in 28.8% (m-equal subset, N=1052: 49.5% / 59.3% / 68.2%). The v2 lock-in is later than n in 547 cases and earlier in 75. Breakdown by scaffold and model: `v1_to_v2_mapping.md` section 3.
- **Which v2 timepoint v1 `n` actually corresponds to.** The v2 prompt declares t_commit 'Same as v1 field n', but empirically n coincides with t_err (57.1% exact) more often than with t_commit (45.8% exact); n == t_err == t_commit in 370 pairs, n == t_err only in 286, n == t_commit only in 156, n before t_err in 161, strictly between in 100, after t_commit in 75. In practice the v1 single marker behaved as an onset marker at least as often as a lock-in marker; the paper should describe `n` as 'the single v1 failure step' rather than as identical to t_commit.
- **Category migration.** The retained `primary_failure_category` string changed in 11.0% of pairs; the three largest v1-category -> v2-trigger cells are `task_strategy` -> `false_premise` (172); `task_strategy` -> `knowledge_gap` (111); `implementation_generation` -> `capability_limit` (72).
- What is **not retained** from this round: per-annotator review assignments, the pre-discussion labels used for the kappa computation (the published kappa CSV is referenced in `rebuttal_review_notes.md`), and the list of records changed during human cross-checking of the LLM drafts.
